# 15. ANDPAD / KANNA と正面衝突しない差別化設計

## 彼らが強い場所

ANDPAD や KANNA は、施工の **記録・共有・デジタル化** で先行している。図面、写真、工程、チャット、帳票、発注者とのコミュニケーションを「現場のOS」として揃えている。

同じ土俵で安く・少しAIを足しても、機能チェックリストで負ける。KenSapo はそこを模倣しない。

## KenSapo が取る場所

**施工管理を、記録する道具から、判断する仕組みへ変える。**

| | 記録SaaS | KenSapo |
|--|----------|---------|
| 中心オブジェクト | ファイル、掲示、日報 | Construction Graph（案件と事実の関係） |
| 現場の作業 | 入力して残す | 撮る・話す・押す。確認は低信頼度だけ |
| 写真 | フォルダ / アルバム | 推定分類。フォルダを作らせない |
| 過去案件 | 検索すれば出る | 聞かれる前に類似の工期・人工・粗利・つまずきを出す |
| 異常 | 人がダッシュボードを読む | 推奨・注意・予測として届く |
| ノウハウ | 個人の頭・別ツール | 工種・建物・トラブルに紐づき次現場の Today に出る |
| AIの出し方 | 機能名になりがち | 結果の一文。モデル名を出さない |
| 最終決定 | システムまたは人 | 必ず人 |

## 正面衝突を避ける具体策

1. **チャット・図面ビューア・検査帳票の完全セットを MVP の勝負にしない。** 必要なら後から、Graph に繋がる範囲だけ。
2. **「安価版」価格訴求をブランドにしない。** 価値は次現場の判断精度。
3. **乗り換えを敵の画面コピーにしない。** CSV/一括で Graph を埋める。相手のIAを再現しない。
4. **経営ダッシュボードをBIの縮小版にしない。** 「今確認すべきこと」だけ。
5. **現場に管理メニューを見せない。** 職人が使うものは Today で完結。

## 競合が後から似てきても残るもの

- 案件IDをハブにした施工データの正規化（写真枚数では負けない）
- 確定キャプチャが人工・材料・進捗・日報・特徴量・シグナルまで一貫して進む書き込み境界
- 類似エンジンと Decision Engine の差し替え可能なインタフェース
- 知識が次の Today に出るループ
- 人間確認を前提にした信頼度設計（幻覚を正にしない）

相手が記録OSであるほど、KenSapo は **その上（または横）で判断精度を上げる層** になれる。最初から相手のOSを置きにいかない。

## メッセージ（対外）

使わない: 「業界最安の施工管理」「AI施工管理」「ANDPAD代替」

使う: 工事をするたびに会社の施工知識が蓄積され、次の現場の判断精度が上がる。

## 既存 KenSapo（kensapo-alpha）との関係

既存は予定・写真・日報の記録アプリである。本リポジトリは別プロダクトとしてゼロから設計する。データ移行が必要になった場合は Ingest 経由で Graph に載せる。スキーマ互換のための妥協はしない。
